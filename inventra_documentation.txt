======================================================
INVENTRA - COMPREHENSIVE PROJECT DOCUMENTATION
======================================================

1. PROJECT OVERVIEW & ARCHITECTURE
------------------------------------------------------
Inventra is a robust, production-ready Inventory Management System designed as a monolithic SaaS application. 

Тех Stack:
- Backend: Vanilla PHP (No framework).
- Database: MySQL (accessed via PDO).
- Frontend: Vanilla JavaScript, HTML5, Vanilla CSS.

Architecture Pattern:
The project follows a custom MVC (Model-View-Controller) structure initialized through a single entry point (the Front Controller pattern). This guarantees that every request must pass through the security, context, and routing configurations defined in `public/index.php` before reaching any business logic.

2. DIRECTORY STRUCTURE & FILE DETAILS
------------------------------------------------------
- /public: The document root exposed to the web server.
  - index.php: The heart of the application. It bootstraps dependencies, intercepts POST forms (via `action` input), processes route requests (via `page` query param), and includes the required views.
  - /css & /js: Static stylesheets and frontend JavaScript scripts.
  - /uploads: Contains user avatars and product images.

- /core: Contains the dependency container (`dependencies.php`) which constructs and injects objects like PDO database connections, Controllers, and Models. It also contains core routing and flash message helpers.

- /models: The Database interaction layer. Each class represents an entity.
  - Product.php: Manages products (`getAll`, `findById`, `create`, `getLowStockProducts`, `getDashboardStats`, etc.). Built using prepared PDO statements to prevent SQL injection.
  - User.php: Handles user directory, profile updates, and role parsing.
  - PurchaseOrder.php, Supplier.php, Category.php, Report.php: Control other database elements.

- /controllers: Contains business logic and input sanitation.
  - productController.php: Takes raw `$_POST` input, validates data types and logic (e.g., SKU uniqueness), processes image uploads safely, and then commands the Product model.
  - authController.php: Manages session control, login checks, and Role-Based Access Control (RBAC). Provides the `->authorize('permission')` mechanisms used universally in `index.php`.

- /views: Pure PHP files comprising the HTML templates. Usually separated by folder (e.g., `/products`, `/dashboard`). They print out variables fetched by `index.php`.

- /database & /config: Stores database migration scripts (.sql) and configuration env files.


3. APPLICATION FLOW: HOW THE WEBSITE OPERATES
------------------------------------------------------
Every interaction consists of a strict HTTP lifecycle controlled entirely by `public/index.php`.

[GET] Viewing a Page Flow:
1. User requests a URL (e.g., `http://localhost/Inventra/public/index.php?page=products`).
2. Bootstrapping: `index.php` calls `require_once __DIR__ . '/../core/dependencies.php'` which initializes the singletons and establishes the database connection.
3. Authentication Gate: The app checks `isLoggedIn()`. If false, includes `views/auth/index.php` and exits immediately.
4. Routing Switch: Evaluates `switch ($page)`. For 'products', it executes:
   - `$authController->authorize('products.view');` (Aborts if role forbidden).
   - `$products = $productModel->getAll(...);` (Fetches data).
   - `require __DIR__ . '/../views/products/index.php';` (Renders the HTML layout populated by `$products`).

[POST] Processing Actions Flow:
1. User submits a form (e.g., clicking "Save Product").
2. The form posts to `index.php` with a hidden field: `<input type="hidden" name="action" value="create_product">` and a `csrf_token`.
3. Action Catch: `index.php` detects `if ($_SERVER['REQUEST_METHOD'] === 'POST')` and intercepts the request before routing.
4. CSRF Validation: Confirms the session token matches the POST token.
5. Action Switch: Executes the specific use case block. e.g., `case 'create_product':`.
6. Delegation: Gives `$_POST` and `$_FILES` to `$productController->handleCreate()`.
7. Session Flash & Redirect: Success or Errors are stored in PHP session (`setFlash()`), and the application outputs an HTTP Redirect (`redirectTo()`) back to a GET route (PRG Pattern).


4. DEEP DIVE: HOW A PRODUCT IS ADDED
------------------------------------------------------
To understand the detailed inner workings, here is the granular sequence of a user adding a product:

A. The UI Form:
The user navigates to `index.php?page=new-entry`. The `views/products/form.php` is rendered. The user inputs Name, Description, SKU, Category (drop-down), Supplier (drop-down), Unit Price, Initial Stock, Minimum Threshold, and uploads a JPG image. The form points to `method="POST"` with `enctype="multipart/form-data"`.

B. Request Intake (`public/index.php` line ~109):
`index.php` hits the POST trap, passes CSRF, evaluates `$action === 'create_product'`, and calls `$productController->handleCreate()`.

C. Validation (`controllers/productController.php`):
`handleCreate()` first calls the internal `validate()` method.
- Evaluates string lengths: `mb_strlen($name) < 3`. 
- Evaluates constraints: Checks if the SKU format matches regex `/^[A-Z0-9-]{4,30}$/`.
- Verifies relations: Ensures integer checks for `category_id` and `supplier_id`.
- Business Rules: Checks if the SKU is already in the database via `$this->productModel->skuExists($sku)`.

D. Image Processing:
If validation passes, `handleImageUpload()` reads `$_FILES['product_image']`.
- Verifies `UPLOAD_ERR_OK` and size <= 2MB.
- Checks strictly against mime types using `mime_content_type()`.
- Renames the file randomly (`bin2hex(random_bytes(12))`) to prevent path traversal and naming collisions.
- Moves it from temp to `/public/uploads/products/`.

E. Database Insertion (`models/Product.php`):
The sanitized array is passed to `$productModel->create()`.
A prepared PDO statement is formulated (`INSERT INTO products (...) VALUES (:name, :sku...)`). The variables are bound and executed, mitigating SQL injection completely. It returns the inserted ID.

F. Resolution:
`index.php` sees the success response from the Controller. It clears the old input cache, sets a success flash message ("Product created successfully"), and utilizes a standard header redirect to the `products` list.


5. USER INTERFACE & DESIGN DETAILS
------------------------------------------------------
The system utilizes a High-Precision Modern SaaS UI.

- Aesthetics: Rather than standard Bootstrap or basic styles, it utilizes a deeply curated "Ethereal Curator" or premium layout. This utilizes a robust color palette, deep contrast for dashboards, clean typography (e.g., Inter/Roboto), and careful use of whitespace.
- Structure:
  - Topbar: Fixed at the apex. Holds the user's avatar, name, system alerts/logs, and overarching controls.
  - Sidebar: The main navigational chassis. Changes dynamically based on permissions (e.g., hide User Management from standard Employees). Built to be sleek with clear iconography.
  - Main Panel: Features grid systems for the Dashboard to easily display stat cards (Total Items, Pending POs) and dynamically responsive data tables.
- JavaScript Enhancements: Vanilla JS is utilized to enrich UX without pageloading. It provides AJAX-assisted search bars across tables, powers modal interactions (e.g., confirmation modals prior to deleting products to prevent accidental data loss), and displays live, auto-dismissing flash toast notifications.


6. SECURITY & MICRO-DETAILS
------------------------------------------------------
- CSRF Protection: Random token generated on session start, forced into every `<form>`, and verified on every `POST`.
- RBAC Architecture: The system checks granular string permissions (e.g., `suppliers.manage`, `reports.sales.daily`) connected to the user's role (Admin, Manager, Staff) during both the POST processing phase AND the GET page rendering phase.
- PRG Pattern: "Post/Redirect/Get" ensures no double-submissions occur if a user refreshes their browser after submitting a form.
- Safe Image Storage: Image extensions are forced via MIME detection, preventing executable PHP from being uploaded disguised as an image. Images drop into an isolated `uploads/` dir.
